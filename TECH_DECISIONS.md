# FocusLens — Technology Decisions

Decisions for Phase 1 (MVP), chosen to satisfy the non-functional budget (<2% CPU, <100MB RAM idle,
2s dashboard load over 90 days, offline-first) and to extend cleanly into Phases 2–3.

## Desktop shell + agent: Tauri 2 (Rust core)

Electron idles at 150–300MB RSS, which already breaks the <100MB budget; Tauri uses the OS webview
and a Rust core, typically idling well under 50MB with negligible CPU. One binary gives us the
tray-resident background agent, native notifications, and the dashboard webview — no separate
daemon process to install or supervise.

## Window focus + idle detection: Rust with OS APIs behind a trait

A 1 Hz sampler reads the foreground window (`active-win-pos-rs`: Win32 `GetForegroundWindow` on
Windows, CoreGraphics/NSWorkspace on macOS) and system idle time (`user-idle`: `GetLastInputInfo` /
IOKit). The sampler feeds a pure-Rust state machine (`tracker::engine`) that is fully unit-tested
without any OS dependency; platform access sits behind a `SystemProbe` trait so Phase 2 platforms
slot in without touching tracking logic.

## Database: SQLite via `rusqlite` (bundled), WAL mode

Embedded, zero-config, offline-first, and the spec names it. We aggregate 1-second samples into
1-minute buckets before writing, so 90 days of heavy use is ~130k rows — indexed range scans return
a day summary in single-digit milliseconds, far inside the 2s dashboard budget. `bundled` removes
any system-SQLite version dependency.

## Dashboard UI: Svelte 5 + TypeScript + Vite

Svelte compiles away its framework, giving the smallest bundle and runtime overhead of the major
options — the right fit for a long-running tray app sharing the resource budget with the tracker.
Vite gives fast dev iteration and is the same toolchain used by the extension build.

## Charts: hand-rolled SVG/CSS bars

Phase 1 needs a totals header and horizontal bar lists. A chart library (ECharts ~1MB, Recharts +
React) is not justified; the Phase 2 heatmap can introduce one if needed.

## Browser extension: Chrome MV3, TypeScript + Vite

Required by spec. A service worker tracks the active tab via `tabs`/`windows`/`idle` events and
attributes elapsed time between events (event-driven, no polling — robust to MV3 worker suspension,
with a 1-minute `chrome.alarms` flush). Tab-session logic is a pure class, unit-tested with Vitest.

## Extension ↔ agent transport: loopback HTTP with a pairing token

The Rust core hosts `tiny_http` bound strictly to `127.0.0.1:48732`. The extension POSTs
minute-bucket events (domain only — never full URLs) with a shared token generated by the agent
and pasted once into the extension popup. Chosen over Chrome native messaging because it needs no
per-browser host registration, works identically for Firefox/Edge in Phase 2, and doubles as the
Phase 3 sync ingestion point. The extension buffers events in `chrome.storage.local` when the
agent is offline (capped, drop-oldest).

## Dashboard ↔ core IPC: Tauri `invoke` commands

The dashboard lives in the same process as the core, so typed `invoke` commands are simpler and
faster than any local REST surface; no port, no serialization beyond JSON.

## Notifications: `tauri-plugin-notification`

Official plugin, native notification centers on both Windows and macOS.

## Repo layout: monorepo with pnpm workspaces

Extension, dashboard, shared TS types (`packages/shared`), and the Rust core change together —
one repo keeps the event schema atomic across producers and consumers and gives a single CI.

## Testing: `cargo test` + Vitest

Spec calls out tracking logic and limit calculations: the tracker state machine, minute-bucket
aggregation, and limit threshold math are pure Rust modules under `cargo test`; the extension
tab-session tracker, offline buffer, and shared time/domain utils are pure TS under Vitest.

## Naming

**FocusLens** is kept — it is descriptive and unclaimed by major tools.
